# Paid WhatsApp order delivery

Open `/delivery-admin.html` from either administration sidebar. After verifying payment yourself, enter the product, plan, duration, paid amount, private payload and instructions. Recipient name and WhatsApp are optional; omitted information is collected when claiming. Confirm the payment checkbox and generate the link. Copy it before leaving the page; its token is intentionally not recoverable from the list.

Send the link directly to its intended recipient. The WhatsApp button prepares a message; it does not send messages automatically. A link is a bearer invitation, not phone verification: anyone holding an unclaimed link can claim it. Do not post links publicly. First claim is atomic and binds the delivery to the signed-in account, or to a random recovery key stored in the guest browser. The URL fragment contains the link token so normal HTTP request/referrer logs do not receive it. No recipient phone is disclosed by the preview.

The recipient opens an illustrated 3D box. Name is required; WhatsApp is required only if not supplied by administration. A signed-in user can recover received orders from `/delivery.html` without the original token. A guest needs the original link and browser storage. Credentials are rendered as text, not HTML, and never stored in browser storage. Unclaimed links expire in 30 days. Existing claim recovery remains available until revoked. Administrators can revoke access; revocation cannot make already viewed/copied credentials secret again.

Every created link adds one paid manual CRM subscription and contact. Claim updates the recipient and marks the order as received. There are no wallet deductions, automatic financial verification, outgoing messages, or automatic account creation. Dates/lifecycle remain pending for the administrator to set in CRM, since durations and warranty dates must not be guessed.

Private payloads are in the non-exposed `master_delivery_private` schema. Client roles have no direct table privileges; RLS explicitly denies direct access. The private security-definer dispatcher intentionally authorizes narrowly scoped RPC actions: admin creation/list/revocation; token-based preview/claim; authenticated-owner or guest-key recovery. The public wrapper is security invoker. Tokens and recovery keys are SHA-256 hashed at rest. Payload text is protected by database access controls and must never be copied into source, logs, CRM notes or audit records. Exact duplicate payloads are rejected to prevent accidental duplicate handover. Differently formatted versions of the same account are not automatically detected; do not create a second link for a single-use account.

Schema: `db/delivery_links.sql`, applied as `private_paid_delivery_links`, plus the explicit deny policy. Regression checks: `tests/delivery-links-security.sql` runs in a transaction and rolls back every fixture, testing admin/payment checks, duplicate payload refusal, bad tokens, preview privacy, claim/retry/second recipient, account and guest recovery, CRM capture, fixed recipient phone and revocation. Production build and public route/privacy checks pass. Full mobile browser/visual acceptance remains a manual check; no real customer orders or credentials were used in verification.
